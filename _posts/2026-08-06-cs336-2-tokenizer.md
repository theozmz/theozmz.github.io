## Preliminary

### `merge_ranks`

This records a ranking for each merging pair. We know the `merges` is like:

```json
[
  ["20", "74"], 
  ["68", "65"], 
  ["20", "61"], 
  ["20", "73"], 
  ...
]
```

And we map each pair to a ranking, which has smaller number i.e. higher priority if its corresponding pair shows earlier.

```python
self.merge_ranks = {pair: rank for rank, pair in enumerate(self.merges)}
```

The code adopts the strategy of "selecting the merge pair with the highest priority (minimum index) each time". This is consistent with the BPE standard algorithm (which always merges the pairs with the highest frequency during training): the higher the frequency of the pairs during training, the higher their rank value in the merge list. Priority is given to trained merging pairs that were merged earlier during encoding, ensuring that the encoding results are consistent with the logic of constructing the vocabulary during training.

### `load_vocab_merges`

`fromhex()` reads hexadecimal number strings and converts them to bytes.

```python
def load_vocab_merges(
    vocab_path: str,
    merges_path: str
) -> tuple[dict[int, bytes], list[tuple[bytes, bytes]]]:
    with open(vocab_path, encoding="utf-8") as f:
        raw_vocab = json.load(f)
    with open(merges_path, encoding="utf-8") as f:
        raw_merges = json.load(f)

    vocab = {int(token_id): bytes.fromhex(token) for token_id, token in raw_vocab.items()}
    merges = [(bytes.fromhex(left), bytes.fromhex(right)) for left, right in raw_merges]
    return vocab, merges
```

### `_encode_chunk`

This part will take an example. Suppose that we have initialized the `vocab` and the `merges`, then we input `"hello world<|endoftext|>"`. The function `def encode(self, text: str) -> list[int]:` will first split the input sequence by special tokens and `"hello world"` will be processed by `def _encode_chunk(self, text: str) -> list[int]:`. The function is like:

```python
def _encode_chunk(self, text: str) -> list[int]:
    ids: list[int] = []
    for match in PAT.finditer(text):
        token_bytes = match.group().encode("utf-8")
        pieces = [BYTE_TOKENS[byte] for byte in token_bytes]

        while len(pieces) > 1:
            best_index = -1
            best_rank = float("inf")
            for i, pair in enumerate(zip(pieces, pieces[1:])):
                rank = self.merge_ranks.get(pair)
                if rank is not None and rank < best_rank:
                    best_index = i
                    best_rank = rank

            if best_index == -1:
                break

            pieces[best_index : best_index + 2] = [pieces[best_index] + pieces[best_index + 1]]

        ids.extend(self.token_to_id[piece] for piece in pieces)
    return ids
```

The `vocab` and `merges` can be in this example:

```python
vocab = {0: b'h', 1: b'e', 2: b'l', 3: b'o', 4: b' ', 5: b'w', 6: b'r', 7: b'd', 8: b'he', 9: b'll', 10: b'o ', 11: b'wo', 12: b'or', 13: b'ld', 14: b'hell', 15: b'world'}

merges = [
    (b'h', b'e'),      # rank 0 → "he"
    (b'l', b'l'),      # rank 1 → "ll"
    (b'o', b' '),      # rank 2 → "o "
    (b'w', b'o'),      # rank 3 → "wo"
    (b'o', b'r'),      # rank 4 → "or"
    (b'l', b'd'),      # rank 5 → "ld"
    (b'he', b'll'),    # rank 6 → "hell"
    (b'wo', b'r'),     # rank 7 → "wor"
    (b'wor', b'ld'),   # rank 8 → "world"
]
```

The chunk `"hello world"` will be processed:

1. The regular expression `PAT` will cut this chunk into several blocks and treat them one by one. After `PAT`, we have `"hello"` and `" world"`. Now we treat `"hello"`.
    ```python
    for match in PAT.finditer(text):
    ```
2. Encode the block into UTF-8 byte string, and divide it into single bytes in a list. The process is: `"hello"` -> `b"hello"` -> `[b'h', b'e', b'l', b'l', b'o']`.
    ```python
    token_bytes = match.group().encode("utf-8")
    pieces = [BYTE_TOKENS[byte] for byte in token_bytes]
    ```
3. Enter the loop: search for all adjacent pairs in `pieces` and find the pair with the highest priority (i.e. the lowest rank) in the `merge_ranks`. Because the key of `merge_ranks` is the merge pair and the value is its index, the smaller the index, the earlier it is merged during training, and the higher the priority.
4. If a combinable pair (`best_index != -1`) is found, the two elements of the pair are merged into a new byte, replacing the original position.
5. Repeat steps 3-4 until there are no merges available (all adjacent pairs are not in the `merge_ranks`).
6. Finally, convert each byte in the final `pieces` into an ID and append it to the result list.

This example:

* **input**: `"hello world<|endoftext|>"`
* **after splitting by special tokens**: `"hello world"`
* **after PAT**: `"hello"` and `" world"`
* `"hello"`
  * `b"hello"`
  * **`pieces`**: `[b'h', b'e', b'l', b'l', b'o']`
  * **`merges` (b'h', b'e')**: `[b'he', b'l', b'l', b'o']`
  * **`merges` (b'l', b'l')**: `[b'he', b'll', b'o']`
  * **`merges` (b'he', b'll')**: `[b'hell', b'o']`
  * **`ids`**: `[14, 3]`
* `" world"`
  * `b" world"`
  * **`pieces`**: `[b' ', b'w', b'o', b'r', b'l', b'd']`
  * **`merges` (b'w', b'o')**: `[b' ', b'wo', b'r', b'l', b'd']`
  * **`merges` (b'l', b'd')**: `[b' ', b'wo', b'r', b'ld']`
  * **`merges` (b'wo', b'r')**: `[b' ', b'wor', b'ld']`
  * **`merges` (b'wor', b'ld')**: `[b' ', b'world']`
  * **`ids`**: `[14, 3, 4, 15]`
* **output**: `[14, 3, 4, 15, 16]`


## Train


Compute the compression ratio:

$$compression\_ratio = \frac{total\_bytes}{total\_tokens}$$

```python
def calc_compression_ratio(tokenizer: Tokenizer, docs: list[str]) -> float:
    total_bytes = 0
    total_tokens = 0
    for doc in docs:
        text = doc.strip()
        if not text:
            continue
        ids = tokenizer.encode(text)
        total_bytes += len(text.encode("utf-8"))
        total_tokens += len(ids)
    return total_bytes / total_tokens if total_tokens else float("inf")
```

Compute the throughput:

$$throughput = \frac{total\_bytes}{total\_time}$$

```python
def measure_throughput(tokenizer: Tokenizer, text: str, n_runs: int = 5) -> float:
    tokenizer.encode(text)
    times = []
    for _ in range(n_runs):
        t0 = time.perf_counter()
        tokenizer.encode(text)
        t1 = time.perf_counter()
        times.append(t1 - t0)
    avg_time = sum(times) / len(times)
    return len(text.encode("utf-8")) / avg_time
```

Encode and save:

```python
def encode_and_save(
    tokenizer: Tokenizer,
    input_file: Path,
    output_npy: Path,
    dtype: type = np.uint16,
):
    total_tokens = 0
    with open(input_file, encoding="utf-8") as f:
        for line in f:
            text = line.rstrip("\n").rstrip("\r")
            if text:
                ids = tokenizer.encode(text)
                total_tokens += len(ids)
    print(f"    total tokens: {total_tokens:,}")

    mmap = np.lib.format.open_memmap(
        output_npy,
        mode='w+',
        dtype=dtype,
        shape=(total_tokens,)
    )

    print("    save token IDs...")
    idx = 0
    with open(input_file, encoding="utf-8") as f:
        for i, line in enumerate(f):
            text = line.rstrip("\n").rstrip("\r")
            if text:
                ids = tokenizer.encode(text)
                mmap[idx:idx + len(ids)] = ids
                idx += len(ids)
            if (i + 1) % 100_000 == 0:
                print(f"    processed {i + 1} lines, total {idx:,} tokens...")

    mmap.flush()
    del mmap
    print(f"    saved {total_tokens:,} tokens to {output_npy}")
```

### 压缩率分析

| 配置 | bytes/token | 说明 |
|:---:|:---:|:---:|
| TinyStories tokenizer on TinyStories | 3.895 | 10K 词表，域内 |
| OpenWebText tokenizer on OpenWebText | 4.344 | 32K 词表，域内，最佳 |
| TinyStories tokenizer on OpenWebText | 3.358 | 10K 词表，跨域，最差 |

### 压缩率结论

1. **OWT tokenizer 在 OWT 上压缩最好**  
   4.344 bytes/token 表示平均每个 token 覆盖约 4.34 个 UTF-8 字节。相比 TS tokenizer 在 TS 上的 3.895，高约 **11.5%**。这来自两点：词表更大（32K vs 10K）且领域匹配。

2. **跨域压缩率显著下降**  
   TS tokenizer 编码 OWT 时只有 3.358 bytes/token，相比 OWT tokenizer 编码 OWT 的 4.344：
   - bytes/token 下降：$$1 - \frac{3.358}{4.344} \approx 22.7\%$$ 这就是 JSON 里的 `efficiency_drop_pct = 22.70`。
   - 等价地，相同字节文本需要的 token 数增加：$$\frac{4.344}{3.358} - 1 \approx 29.4\% $$ 也就是说，用 TinyStories tokenizer 编码 OpenWebText，序列长度会增加约 **三成**。

3. **跨域比“小词表本身”影响更大**  
   TS tokenizer 在 TS 上还有 3.895 bytes/token，但在 OWT 上降到 3.358，下降约 **13.8%**。说明 OWT 中大量词、符号、URL、代码、专名等模式不在 TinyStories 的 10K 词表中，被拆成更细的字节/短子词，导致 token 碎片化。

4. **对训练和存储的影响**
   - 序列变长：同样上下文窗口能覆盖的原始文本更少。
   - 训练计算量增加：每 token 都参与 Transformer 计算，token 数多约 29%，训练成本上升。
   - 存储增加：Pile 825GB 若用 OWT tokenizer，约 $$ 825 \times 10^9 / 4.344 \approx 1900 \text{ 亿 token} $$ uint16 存储约 **380GB**。  
     若用 TS tokenizer 编码 OWT 类文本，约 $$ 825 \times 10^9 / 3.358 \approx 2457 \text{ 亿 token} $$ uint16 约 **491GB**。差距约 110GB。

### 吞吐量分析

JSON 中：

- OpenWebText tokenizer 吞吐量：  
  **0.444 MB/s**  
  即约 **444 KB/s**，约 **0.000444 GB/s**。
- 测试文本大小：0.971 MiB。
- Pile 825GB 单遍估算：  
  **1,856,222 秒 ≈ 515.6 小时 ≈ 21.5 天**。

### 吞吐量结论

1. **0.444 MB/s 非常慢**  
   这是纯 Python BPE 实现的典型表现。`_encode_chunk` 对每个预分词片段反复扫描所有相邻 pair，每轮只合并一个最低 rank 对，然后重新扫描。对长度为 $$L$$ 的片段，复杂度接近 $$O(L^2)$$ 或更差，且涉及大量 bytes 拼接、dict 查找和 Python 循环。

2. **Pile 单遍 21.5 天只是理想 CPU 编码时间**  
   该估算：
   - 只计算 `tokenizer.encode` 的时间；
   - 不包含读文件、写 `.npy`、memmap 刷新、I/O 等待；
   - 使用 OWT 前 200 行重复构造的约 1MB 文本，代表性有限；
   - 未考虑 Pile 本身领域更杂，压缩率和片段长度可能不同。

3. **实际 `encode_and_save` 会编码两遍**  
   `encode_and_save` 第一遍扫描统计总 token 数，第二遍再编码并写入。两遍都调用 `tokenizer.encode`，所以当前实现下，Pile 全量编码单线程实际约为：$$21.5 \times 2 \approx 43 \text{ 天}$$ 这还没有计入 I/O 和写盘开销。

4. **多进程可显著缩短，但仍有上限**  
   理想情况下：
   - 8 进程：约 $$43 / 8 \approx 5.4$$ 天；
   - 16 进程：约 $$43 / 16 \approx 2.7$$ 天。  
   实际会受磁盘 I/O、内存带宽、进程调度和负载均衡影响。

5. **测试本身偏小，结果有噪声**  
   测试 chunk 只有约 0.97 MiB，`n_runs=3`，单次编码约 2 秒，容易受系统缓存、CPU 频率和后台负载影响。建议至少用 10–100MB 文本、更多轮次、取中位数，并报告标准差。
